# Benchmark methodology

The headline result is that **the Zig port is slower than the C original on 9 of
12 workload/mode pairs**. This document exists so that number can be checked,
reproduced, and argued with.

Regenerate everything: `make bench` (or `python3 scripts/bench.py --repetitions 5`).

## What is measured

Both harnesses do the same work. `oracle/bench_c.c` links the pinned upstream
`pdjson.c`; `tools/bench_zig.zig` uses the Zig library. They mirror each other in
structure deliberately — same parse loop, same counting allocator, same warm-up
policy, same output format. If they did different amounts of work, the comparison
would be meaningless.

The loop is upstream's own streaming pattern: `json_next` until `JSON_DONE`, then
`json_reset` and continue until a second `JSON_DONE`. In `strings` mode it also
calls `json_get_string` on every string and number event, which exercises the
token buffer rather than just the event machinery. Event counts are accumulated
into a checksum that is printed, so the loop cannot be optimised away.

## Fairness controls

These are enforced by `scripts/bench.py`, not asserted in prose.

- **Identical inputs.** The workloads in `bench/workloads/` are committed
  generated files, byte-identical across machines and runs.
- **Warm-up is unrecorded.** One cold iteration (timed separately and reported as
  `cold_ns`) plus four warm iterations, then measurement begins. Allocation
  counters are reset after warm-up.
- **Binaries are interleaved within each repetition.** C, Zig-ReleaseSafe and
  Zig-ReleaseFast run back to back for each repetition, so thermal drift and
  background load are spread across all three rather than concentrating in
  whichever ran last.
- **Same clock on both sides.** `clock_gettime(CLOCK_MONOTONIC)` via libc in both
  harnesses — the Zig side calls `std.c.clock_gettime` rather than a Zig-native
  timer specifically so the two sample sets are directly comparable.
- **Same allocator on both sides.** Both install a counting allocator over the
  system `malloc`/`realloc`/`free`, so allocator behaviour is shared and is not
  part of what is being compared. It also adds the same small constant cost to
  both.
- **Every sample is kept.** `bench/results/raw.json` holds all per-iteration
  samples, not a pre-cooked average. The summary is derived from it and can be
  recomputed without re-running.
- **Both Zig modes are reported.** ReleaseSafe is what the project ships;
  ReleaseFast is the closest like-for-like against C's `-O2`. Quoting only the
  faster one would be dishonest.

### Clock granularity

`CLOCK_MONOTONIC` resolves to 1 µs on this macOS build. The `malformed-early`
workload rejects its input on the first byte and parses in well under that, so
its first measured run produced nothing but `0` and `1000` — a median of zero and
a division by zero in the summariser.

Rather than dropping the workload or reporting the noise, each sample now covers
an `inner` batch of parses (5,000 for `malformed-early`, 1 elsewhere), and the
summariser divides `inner` back out. Every reported figure is per parse.

## Optimisation levels

| | |
| --- | --- |
| C | `-O2 -std=c99` |
| Zig (shipped) | ReleaseSafe — bounds checks, overflow checks and illegal-behaviour detection **active** |
| Zig (comparison) | ReleaseFast — checks disabled |

Upstream's own Makefile passes no `-O` flag at all. Benchmarking against `-O0`
would have been flattering and meaningless, so `-O2` is used.

A note on how this was nearly got wrong: Zig's `standardOptimizeOption` defaults
to **Debug** unless `--release` is passed. The first benchmark run reported the
Zig side as 6.8× slower than C, which was simply the cost of a Debug build. The
build now defaults to ReleaseSafe for a bare `zig build` (DECISIONS.md D-10),
because the mode that ships is the mode that should be measured.

## Results and what explains them

Current numbers are in [`artifacts/benchmark-summary.json`](../artifacts/benchmark-summary.json)
and reproduced in the README's generated table. Ratios are C median ÷ Zig median;
below 1.00 means Zig is slower.

Two observations that matter more than the individual figures:

**ReleaseSafe and ReleaseFast are within about 2% of each other.** So the gap
against C is *not* the cost of Zig's safety checks. Bounds and overflow checking
are close to free on this workload set, which is the more interesting result:
the port ships with them on and pays almost nothing for it.

**The one large Zig win is not throughput.** `malformed-early` rejects on the
first byte, so it measures open/close overhead. It is reported because excluding
inconvenient-shaped results in either direction would be selective.

### Profiling: the first hypothesis was wrong

The initial gap was 0.57×–0.70×. My hypothesis was that the null checks the port
adds on the source function pointers (`orelse return EOF`, which C does not have)
were the cost. I built a variant with those removed and measured:

```
flat-ints      C=3.662ms  zig-shipped=5.354ms (0.68x)  zig-no-nullchecks=5.358ms (0.68x)
numbers        C=3.478ms  zig-shipped=5.084ms (0.68x)  zig-no-nullchecks=5.217ms (0.67x)
large-mixed    C=3.882ms  zig-shipped=5.546ms (0.70x)  zig-no-nullchecks=5.673ms (0.68x)
```

**0% of the gap.** The hypothesis was simply wrong, which is recorded here
because a plausible-sounding explanation that goes unmeasured is how benchmark
prose usually goes astray.

Leaf-weighted profiles of both binaries on `flat-ints` (macOS `sample`, 3s)
showed the actual causes:

```
=== C -O2 ===                          === Zig ReleaseFast ===
 23.0%  read_digits                      21.4%  parser.bufferPeek
 19.1%  buffer_peek                      18.2%  parser.pushchar
 18.6%  buffer_get                       17.0%  parser.readValue
 16.1%  read_value                       16.6%  parser.readDigits
  9.3%  json_next                        15.9%  parser.bufferGet
  4.9%  _platform_memchr                  7.2%  parser.nextEvent
  2.1%  DYLD-STUB$$memchr                 2.8%  parser.nextChar
```

Two differences stand out:

1. **C has no `pushchar` frame at all** — clang inlined it into `read_digits`
   (23.0%). Zig kept it as a separate call: `readDigits` 16.6% *plus* `pushchar`
   18.2% = 34.8%. Fix: split `pushchar` into an `inline` fast path and an
   out-of-line growth path, so the hot path is inlined without duplicating the
   realloc logic at fifteen call sites.

2. **C spends 7% in `memchr`** — the `strchr` calls in `read_number`. The port was
   using `std.mem.indexOfScalar` for the same thing. Both were replaced with
   direct comparisons, preserving the detail that C's `strchr` also matches the
   terminating NUL (which the original relies on by accident for input like
   `1\x00`).

Combined effect: `large-mixed` 0.70× → 0.87×, `flat-ints` 0.67× → 0.80×.

Correctness gated every step. After each change the full differential corpus
(1,926 comparisons), the upstream suite, and the Zig test suite were re-run; all
stayed at zero divergences and 18/18.

### What is still unexplained

The remaining ~10–20% on the number-heavy workloads is not accounted for. The two
profiles now have the same shape and roughly the same distribution, which
suggests it is spread across the whole event loop rather than concentrated in one
place — possibly instruction selection or register allocation differences between
LLVM's C and Zig front ends at the same optimisation level.

It is left unexplained rather than chased, because optimising further against
this specific workload set would risk exactly what this project is trying to
avoid: tuning for the benchmark instead of for the behaviour. Correctness gates
performance claims, not the other way round.

## Confounders

Recorded in the artifact and repeated here:

- Run on a laptop, not an isolated machine. Other processes and thermal
  behaviour affect absolute numbers; interleaving mitigates but does not remove
  this.
- Both harnesses install a counting allocator, which adds a small constant cost
  to both.
- `malloc`/`realloc` come from the system allocator in both cases.
- Single architecture (arm64 macOS) for the published figures. CI runs the
  smoke benchmark on x86-64 Linux, but the full run is not published from there.
- Medians over 5 repetitions × 30–200 iterations each. Distribution summaries
  (mean, stdev, p95, p99, min) are in the artifact; the tables quote medians.
